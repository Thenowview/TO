## P0 — Windows and agent execution (blocking core autonomy)

1. **Controlled tool runtime:** Implement an allowlisted typed action registry, per-action input schemas, paths scoped to approved workspaces, explicit effect classification and authorization receipts. Never evaluate raw model shell text as code. A terminal-capable agent must propose a concrete script/argv for human inspection; no unrestricted ambient administrator access.
2. **Tool results and evidence:** Every action records request digest, operator identity, decision, start/end timestamps, exit code, bounded stdout/stderr, data classifications, and before/after state. If an action may have executed but returned unusable evidence, mark `needs_review`; do not automatically retry side effects.
3. **Secure process management:** Run as an unprivileged Windows user or disposable VM; enforce timeout, process-tree termination, concurrency limits and resource caps. Do not bypass SmartScreen, UAC, antivirus, or GitHub branch protections.
4. **Durable orchestration:** Keep dependency graph, approval state, attempts and evidence in SQLite. After a restart mark uncertain external work interrupted/needs review; only explicitly approved idempotent actions can be retried.
5. **GitHub integration:** Scoped GitHub API or CLI authentication. Read workflow runs, check runner labels, select trusted branch and dispatch a manually approved workflow; register a runner only with explicit owner approval and a short-lived registration token handled in memory, never logged.
6. **Development/QA:** Run real OpenCode on an isolated copy with an explicitly chosen model and supported permissions. No automatic edit-to-main; produce a reviewed Code Studio proposal, synthetic and integration tests, plus independent QA.

### P0 acceptance scenario: self-hosted GitHub runner

- On Windows x64, **identify** the existing runner from either `%USERPROFILE%\Downloads\actions-runner` or `C:\actions-runner`. Read only presence and known filenames; never read or display `.credentials`, `.credentials_rsaparams`, or token content.
- Propose the official GitHub download URL and hash expected from the current GitHub setup page; do not trust a version/hash generated by a model. Verify SHA-256 before extraction. Downloads and installation require a distinct approval.
- Obtain a fresh registration token via an authorized GitHub API operation or a direct private user prompt. Do not echo the token, persist it in transcripts or hand it to an unrelated model/tool.
- Register runner with label `theorg-win` on an isolated low-privilege host. Starting or installing a Windows service requires separate approval.
- Verify real GitHub **Online/Idle** and labels through the authenticated provider API or the user-visible runner page. Local `.runner` presence proves only local registration metadata, never Online status.
- Manually dispatch source-only `bridge-ci.yml` on the trusted branch with `confirm_self_hosted=true` and `build_unsigned_windows_candidate=false`.
- Read the actual run logs/results. If failures exist, offer a reviewed source fix in a draft branch, rerun source tests, and show the execution evidence. Do not fake results or merge/release without passing checks.

## P1 — Desktop, browser and release

- Desktop UI automation needs window/process identity, visible focus, guarded typing, credential prompts handled by the user, screenshot-aware state checks, and safe cancellation. Do not automate authorization dialogs.
- Browser tools need URL/domain and network allowlists, read-only versus write action separation, bounded downloads, permission scopes, and clearly visible side effects.
- Deliver an executable Windows x64 package with reproducible source revision, checksums, engine/native bridge self-tests, signing decision and a clean-machine smoke test.
- Require accessibility, restart/interruption, isolation, no-secret-leak, and rollback verification before promotion from developer preview.

## P2 — Business integrations

- Implement individual connectors for approved mail, files, calendars and other services only after P0 permission policies and audit records are reliable.
- Read/write scopes must be explicit and revocable. Email sending, deletions, calendar edits and external sharing require reviewable side-effect previews and approvals.
- Do not infer success from a model response. Each integration must produce provider-confirmed receipts and test a revoked/expired/denied credential state.
- Keep no-paid-services mode as an enforceable policy: provider cost estimates and a per-action deny control, not a marketing promise.
